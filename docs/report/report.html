Executive summary

On sales days, order traffic reaches about three times a normal day, at times nobody can schedule. Today's fixed fleet either sits mostly idle or slows down at the peak. We recommend one public Application Load Balancer in front of an EC2 Auto Scaling group in private subnets across two Availability Zones. A CPU target-tracking policy adds servers during the rush and removes them afterwards.

A Regional NAT Gateway gives the servers outbound-only access to updates. Admin access goes through Systems Manager, so no admin ports are open. The whole environment is defined in CloudFormation and deployed from Git through Git sync, so it can be rebuilt from the repository at any time.

PART AWhat we found

1The problem

Onward Logistics runs its order system on a fixed set of servers. On sales days demand jumps to roughly three times normal, and nobody can predict exactly when it will start.

The dilemma today

Size for the peak and pay for idle servers about 95% of the month, or size for a normal day and slow down or fail exactly when merchants need the system most. One server or Availability Zone failure can also take orders offline.

3Impact of doing nothing

Lost orders and merchants

Slow pages and errors at the peak turn away customers exactly when demand and revenue are highest.

Damaged trust

Merchants who rely on Onward on their busiest day move to competitors after one bad sales day.

Night-time firefighting

Engineers add servers by hand under pressure, with a high risk of mistakes and burnout.

Paying for idle capacity

The only "safe" alternative is a peak-sized fleet all month, about 3× the compute bill.

Single point of failure

A single server or data-centre (AZ) outage takes the order system offline.

Exposed servers

Publicly reachable servers and open admin ports widen the attack surface.

4Security and resilience patterns

Public ALB, private compute

Only the load balancer has a public address. Servers sit in private subnets with no public IPs.

Security group chaining

The app port accepts traffic only from the ALB's security group: no CIDR rules, no port 22.

Outbound-only internet

A Regional NAT Gateway lets servers fetch updates but blocks all inbound connections.

Multi-AZ self-healing

Two AZs, minimum 2 servers, ELB health checks: failed servers are replaced automatically.

No admin ports

SSM Session Manager and Run Command over HTTPS replace SSH and bastion hosts.

Secrets and least privilege

Token in Secrets Manager, IAM managed policies only, IMDSv2 enforced.

PART BBusiness value

1Chosen approach

A single internet-facing Application Load Balancer is the only public entry point. Behind it, an EC2 Auto Scaling group of small t3.micro servers runs in private subnets across two Availability Zones. A target-tracking policy keeps average CPU near 50%, adding servers (up to 6) during a sales rush and removing them (down to 2) afterwards. Nobody has to touch it.

Each new server installs the order application itself at boot from a pinned Git release. Each page shows which server and AZ answered. A Regional NAT Gateway lets the servers download updates without being reachable from the internet. Everything is defined in one CloudFormation template that deploys automatically from Git through Git sync, so the environment can be rebuilt from the repository.

Scale out

CPU above 50% → CloudWatch alarm → ASG launches servers (max 6).

Scale in

After ~15 min of low CPU the ASG removes extra servers (min 2).

Self-heal

Failed /health → ALB marks the server unhealthy → ASG replaces it.
